# 使用说明

## 这个仓库解决什么问题

网上的儿童学习资源不是不够，而是**散**：一部分在群聊截图里，一部分在网盘分享码里，一部分在"50 个免费网站"这类清单里。它们共同的问题是：

- 链接挂了你不知道，照抄一遍，白折腾；
- 资源没有按年龄和科目归档，找的时候得重新判断一遍适用性；
- 工具推荐混着软文，写的人自己没跑过。

所以这里的每条链接都过一遍探针，标注状态和时间；每份资料都写清科目、年级、载体、来源。

想先知道这个仓库踩过哪些坑、为什么这么设计，看 [09-开发复盘](09-开发复盘.md)。

## `data/resources.json` 是唯一数据源

所有清单都从这一个文件生成。它分成七个区：

| 字段 | 内容 | 条目数 |
| --- | --- | --- |
| `websites` | 免费学习网站 | 74 |
| `tutoring` | 线上口语一对一平台（含支付方式与主体） | 15 |
| `repos` | 开源项目 | 22 |
| `videos` | 按教材版本登记的在线视频课程 | 61 |
| `mcp_tools` | Cursor 可用的 MCP 工具与命令行工具 | 12 |
| `dify` | Dify 数据源与插件 | 11 |
| `collections` | 网盘成套资料 | 59 |

`collections` 里混了两种统计口径，看条目上的 `share_probe_depth` 区分：

| 口径 | 条件 | 报告什么 | 正文 |
| --- | --- | --- | --- |
| 全量 | 无 `share_probe_depth` | 真实文件总数、总字节、扩展名分布 | [03b-网盘资料清单](03b-网盘资料清单.md) |
| 浅层 | `share_probe_depth: "shallow"` | 只报第 2 层有几个目录/文件，**不报文件总数** | [03c-教辅成套清单](03c-教辅成套清单.md) |

浅层口径是给教辅包用的：它们的结构是「1 个总目录 → 几十个教辅目录 → 再按年级分册」，全量遍历一条要几分钟，44 条要好几小时。所以只报到第 2 层，用「第 2 层 66 项」这样的结构量描述规模，不虚报总数。

每条网站记录形如：

```json
{
  "id": "nrich",
  "name": "NRICH",
  "category": "数学",
  "age": "5+",
  "url": "https://nrich.maths.org",
  "verified": "blocked",
  "note": "剑桥数学问题库，按学段分级",
  "lang": "en",
  "checked_at": "2026-11-09T11:48:44+08:00"
}
```

### `verified` 的六个取值 <a id="verified-的六个取值"></a>

| 值 | 含义 | 你该怎么做 |
| --- | --- | --- |
| `ok` | HTTP 2xx | 直接用 |
| `blocked` | 站点反爬（403/429） | 用浏览器打开，通常正常 |
| `dead` | 域名不存在或站点已关停 | 别用了，找替代入口 |
| `unreachable` | DNS 正常但本机连不上 | 需要代理，或换网络环境 |
| `mismatch` | 链接可达，但页面内容与描述不符 | **人工标记，脚本不覆盖**，需自行判断是否采用 |
| `pending` | 未探测 | 运行脚本 |

`checked_at` 记的是最后一次核验的时间戳。**如果这个时间已经过去几个月，先跑一遍脚本，再采信 `verified`。**

### `tutoring` 分区多一组人工字段

`tutoring` 只把 `verified` / `checked_at` 交给脚本，支付与师资是人工核对的结论：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `operator` | 自由文本 | 服务条款或联系页写明的主体，不看有没有中文站 |
| `alipay` | `official` / `official_manual` / `none` / `unverified` | 前两者=官方在线结账 / 官方渠道收款；`none`=官方支付说明列全且不含支付宝；`unverified`=只有间接证据 |
| `alipay_evidence_url` | URL | 支撑该结论的官方页面 |
| `fixed_teacher` | 支持 / 可预约 / 待确认 | 「可预约」指每次都要自己抢时段，没有自动固定排课 |

**`alipay` 是人工结论，探针不会写它。** 官网支付说明页返回 200 不代表支持支付宝。细则见 [12-线上口语一对一](12-线上口语一对一.md)。

## 怎么核验链接

```bash
python scripts/check_links.py                    # 全量报告，不改文件
python scripts/check_links.py --only websites    # 只看网站分区
python scripts/check_links.py --only quark_tree  # 全量翻完夸克分享目录，拿真实文件数
python scripts/check_links.py --only quark_shallow  # 只翻 2 层，用于大批量教辅包
python scripts/check_links.py --only sheet_index    # 统计腾讯文档索引里内嵌的夸克链接
python scripts/check_links.py --write            # 回写 verified / checked_at / final_url
```

## 下载视频

```bash
python scripts/download_video.py --check                    # 自检环境
python scripts/download_video.py <URL>                      # 最高 1080p + 字幕
python scripts/download_video.py <URL> --audio-only         # 只要音频
python scripts/download_video.py <URL> --output D:/videos   # 换目录
```

底层是 `yt-dlp`（1755 个提取器，B站/YouTube 都支持）。文件落到 `downloads/`（已忽略），清单追加到 `downloads/manifest.jsonl`。

**三条硬限制**，先知道能省很多排查时间：

1. **下不了国内网盘**。实测夸克、百度、阿里、115、迅雷、天翼、彩云全部无提取器。网盘里的 mp4 得先用网盘客户端或 `BaiduPCS-Go` 落盘。
2. **`--cookies-from-browser chrome` 在 Windows 上不可用**。Chrome 运行时会独占锁 Cookie 库，且 127+ 用 App-Bound Encryption，密钥需要 SYSTEM 层 DPAPI 才能解。本机实测 3446 条 Cookie 全是 v20，用户态无解。用 `python scripts/check_chrome_cookies.py` 可自检。要用登录态就导出 `cookies.txt`（用完即删），或改用 Firefox。
3. **B站字幕需要登录**。无登录态时视频能下，`.srt` 不会产出。

## 检查 Chrome Cookie 能否被外部工具读取

```bash
python scripts/check_chrome_cookies.py
```

三层检测：文件可读性 → 加密格式（v10/v20）→ 主密钥可解性。用来回答「为什么 yt-dlp 的 `--cookies-from-browser chrome` 一直失败」。

**不要套 `timeout` 运行**：MSYS 的 `timeout` 会丢弃 `LOCALAPPDATA`，脚本会定位不到 Chrome 目录。

分区可选：`websites` / `tutoring` / `repos` / `videos` / `collections` / `markdown` / `quark_tree` / `quark_shallow` / `sheet_index`。

脚本行为说明：

- 只用标准库，Python 3.10+ 直接跑，不需要 `pip install`；
- 12 个并发，单条超时 20 秒；74 条网站约 10 秒，websites + tutoring + repos + collections 共 158 条约 20 秒；
- 遇到「200 但重定向至关停公告」会判 `dead`，不会因为状态码好看就放过；
- 遇到 403/429 判 `blocked` 而不是 `dead`——这类站点（Smithsonian、Britannica Kids、Science Buddies）在浏览器里是可以正常打开的；
- 遇到连接失败会先做一次独立的 DNS 解析，区分「域名没了」和「网络连不上」。这两个结论对使用者的意义完全不同。

### `quark_tree` 分区：真的把分享目录翻完

这一分区走夸克公开接口（`sharepage/token` + `sharepage/detail`），**不需要登录**，能拿到分享里每个文件的名字与大小。

两个绕不开的服务端限制：

1. **单页硬限 100 条**。传 `_size=1000` 也只返回 100，必须翻页。
2. **大分享要跑很久**。`quark_misc`（爆笑初中9科）实测 **21943 个文件、1534 次请求、约 11 分钟**。默认预算 `QUARK_REQUEST_BUDGET = 2000`，单条可在数据里用 `share_request_budget` 覆盖。超限时置 `share_tree_truncated`，**不把半个目录当成完整结果报数**。

早期把预算设成 400，`quark_misc` 被截断成 6899 —— 真实值的 1/3。这个教训写进了默认值。

还有一个必须处理的坑：**请求失败 ≠ 目录到底**。早期版本把超时当成空页，导致同一分享两次统计相差 40 个文件。现在单页失败重试 3 次（`QUARK_PAGE_RETRIES`），仍失败则记 `share_tree_failed_pages`、置 `share_tree_incomplete`。

产物写进 `data/resources.json` 的 `collections`：

| 字段 | 含义 |
| --- | --- |
| `share_total_files` | 实测文件数（截断或有失败页时是下限） |
| `share_total_size_bytes` | 实测总字节数 |
| `share_suffix_counts` | 按扩展名分布 |
| `share_tree_truncated` | 是否因请求预算用尽而截断 |
| `share_tree_failed_pages` | 重试 3 次后仍失败的页数 |
| `share_tree_incomplete` | 上面两项任一为真时置 `true`，表示数字是下限 |
| `share_tree_requests` | 实际发出的请求次数 |
| `needs_passcode` | 是否需要提取码（用空码单独试一次判定，不是靠带码成功推断） |
| `tree_checked_at` | 本次统计时间 |

不改动已有的 `actual` / `note` 等人工复核过的描述字段。

### `quark_shallow` 分区：大批量教辅包的浅层口径

教辅包（小学预习复习包、初中全科套件）的结构是「1 个总目录 → 几十个教辅目录 → 每个子目录再按年级/版本分册」。全量遍历一条要几分钟，44 条要好几小时，实际也不需要——使用者关心的是「这一包收了哪些教辅」，不是总字节数。

所以这一分区固定只翻到第 2 层：

```bash
python scripts/check_links.py --only quark_shallow --write
```

44 条实测约 110 秒（单包 1-10 次请求），报告形如：

```
[OK  ] quark_shallow p_chn                      第2层  66 项（目录  66 / 文件   0）   10 次请求
```

| 字段 | 含义 |
| --- | --- |
| `share_top_name` | 顶层目录名，用于确认分享标题与实际内容是否一致 |
| `share_l2_entries` | 第 2 层总项数 |
| `share_l2_dir_count` / `share_l2_file_count` | 第 2 层里目录与文件各多少 |
| `share_l2_dirs` | 第 2 层目录名（上限 80 个） |
| `share_l3_dir_names` | 第 3 层抽样，只用于说明「内容还在更下面」 |
| `share_probe_truncated` | 请求预算用尽 |
| `share_probe_requests` | 实际请求次数 |
| `share_probe_checked_at` | 本次探测时间 |

**这一分区不写 `share_total_files`。** 第 2 层的文件数是按层计的，不是资料规模——实测「初中电子课本」第 2 层只有 36 个文件，但第 3 层有 164 个目录，PDF 全在下面。写进去会让人误以为是全量。

第 3 层采用抽样（取前 8 个目录各翻 1 页），**抽样不置 `truncated`**——截断标记只表示第 2 层本身没读全，把抽样算成截断会让标记失去意义。

标了 `share_probe_depth: "shallow"` 的条目会被全量分区 `quark_tree` 主动跳过，两个分区互斥。

### `sheet_index` 分区：腾讯文档总索引

```bash
python scripts/check_links.py --only sheet_index --write
```

腾讯文档把表格数据放在 percent-encoded 的 `flyweight.texts` 里，脚本整体 unquote 后数 `pan.quark.cn/s/<id>` 的出现次数。标题不在明文（明文的 `<title>` 是通用的「腾讯文档」），要从 base64 的 `basicClientVars` 里解 `padInfo.padTitle`，解不出就留空不猜。

| 字段 | 含义 |
| --- | --- |
| `sheet_title` | 表格真实标题 |
| `sheet_embedded_quark_links` | 内嵌的夸克分享链接条数 |
| `sheet_embedded_quark_links_unique` | 去重后条数 |

这三个索引是导航页，不是资料本体。

### 人工结论的处理

`verified` 为 `mismatch`，或条目上带 `status_manual: true` 时，脚本跳过该条不回写。

原因是夸克分享被平台下架时**分享页仍返回 HTTP 200**（前端兜底页），只有接口层的业务码 `41010` 能看出来。这种情况如果让脚本重探，会把人工判定的 `dead` 冲成 `ok`。实测样本：`j_53_zhongkao`。

## 贡献约定

1. **新增链接必须带 `verified` 与 `checked_at`**。不要手填 `ok`，跑脚本生成。
2. **新增网盘资料必须写清 `entry_type`**：是官方直链，还是第三方中转域名。中转域名要单独记在 `collections/` 里作为别名。
3. **不要声称未经核实的功能数量、课时数、覆盖范围**。原始文案里的「900 节」「57 种工具」这类数字，要么核对过，要么在 `note` 里明确写「为原始文案，未逐一核对」。
4. **不要收录需要破解、绕过付费墙的资源**。
5. **不要提交可执行文件**。工具一律给安装命令，不给二进制包。本地工具放 `.tools/`（已忽略）。
6. **不要把 Cookie、access_token 等明文凭据写进任何入库文件**。放 `.credentials/netdisk.env`（已忽略），用 `scripts/run_netdisk_mcp.py` 注入。

## 已知的坑（免得你重复踩）

- **Windows 控制台默认 GBK**：直接跑带中文输出的脚本会乱码。本仓库的脚本已在 `main()` 里把 stdout 重定向为 UTF-8，但你自己写脚本时要注意。
- **`python -` 走 heredoc 时中文路径容易出问题**：涉及中文文件名的操作，优先用绝对路径而不是相对路径。
- **`nslookup` 返回 `Address: 223.5.5.5` 不代表域名可达**，那只是 DNS 服务器地址。判断域名是否存在，用 `socket.getaddrinfo` 或 DoH 查询的 `Status` 字段（0 = 存在，3 = NXDOMAIN）。
- **`ERRNO 2 No such file or directory` 在 Windows 上可能是 DNS 失败**，Python 的 `URLError` 会把 `EAI_NONAME` 包成 `OSError(2)`。别把它当成文件不存在。
- **MSYS 的 `timeout` 会丢弃部分环境变量**：实测 `timeout 60 python -c "print(os.environ.get('LOCALAPPDATA'))"` 输出 `None`，而直接跑能拿到值。凡依赖 `LOCALAPPDATA` / `USERPROFILE` 的脚本，别套 `timeout`，或者脚本内部做好回退。
- **PowerShell 在 MSYS 里调 `cmd` 会解析错路径**：`cmd` 被解析成 `C:\msys64\usr\bin\cmd`，报 `Cannot run a document in the middle of a pipeline`。写 PowerShell 片段时避开 `cmd`。
- **`\\?\GLOBALROOT\Device\...` 这类设备路径**：Python 的 `open()`、.NET 的 `Test-Path` / `Copy-Item` 都会判「不存在」。要用 Win32 `CopyFileW`（ctypes 调 kernel32）。

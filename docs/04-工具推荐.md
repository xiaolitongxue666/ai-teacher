# 工具推荐

网盘下载与 PDF OCR，在 Cursor 和 Dify 两条路线上选型完全不同。这份文档只写**跑过、核实过**的东西，并把原始推荐里经不起验证的说法单独列出来。

- 数据源：`data/resources.json` 的 `mcp_tools` 与 `dify` 段
- 核验方式：npm registry / PyPI JSON API / GitHub API 逐个查版本、发布时间、仓库和描述
- 版本复核：`data/resources.json` 的 `mcp_tools` 每条带 `latest_version_checked`（registry 当前 latest），与 `version` 不一致即说明登记值已过时
- 核验时间：2026-11-09（MCP 包版本 11:47，Dify 插件目录 11:47）

---

## 一、先看结论

### Cursor（要的是「AI 能直接操作文件和读文档」）

| 需求 | 首选 | 命令 | 为什么 |
| --- | --- | --- | --- |
| 接坚果云 / Nextcloud / ownCloud | `webdav-mcp-server` | `npx -y webdav-mcp-server` | 通用 WebDAV，19 star，不绑定单一网盘 |
| 接百度 / 阿里 / 115 / 夸克 / OneDrive | `sync-vault-agent` | `npm i -g sync-vault-agent && mcp-agent init` | 唯一声称全覆盖的，但要谨慎 |
| 本地 PDF → Markdown（首选） | `pymupdf4llm-mcp` | `uvx pymupdf4llm-mcp` | PyMuPDF 官方，73 star，纯本地无 Key |
| 本地 PDF，要大纲和表格 | `pdffr-mcp` | `npx -y pdffr-mcp` | 三个专用工具，轻量 |
| OCR 能力更全 | `mcp-pdf` | `uvx mcp-pdf` | 文本 + OCR + 表格 |

**最省事且不引狼入室的组合**：`webdav-mcp-server` + `pymupdf4llm-mcp`。两个都是本地直传、无需 API Key、不经过第三方服务器。代价是坚果云以外的网盘接不进来。

### Dify（要的是「给 RAG 知识库准备高质量数据」）

| 需求 | 方案 | 状态 |
| --- | --- | --- |
| OneDrive / Google Drive / Box / S3 / 腾讯 COS | 官方 datasource 插件 | 已验证存在 |
| 坚果云等 WebDAV 网盘 | 社区插件 `shaba/dify-datasource-webdav` | 仅 1 star，需自行评估 |
| 工作流里按路径取 WebDAV 文件 | 官方 `nextcloud` tool 插件（v0.1.7） | 已验证存在，但**不能作为知识库数据源** |
| 扫描版 PDF 解析（首选） | MinerU 官方插件 | 已验证存在于官方插件库 |
| 中文 OCR | PaddleOCR 官方插件 | 已验证存在 |

**原生组合**：官方云存储数据源（或 WebDAV 社区插件）+ MinerU。这是唯一全程不脱离 Dify 生态的方案。

## 二、Cursor 侧：逐个核实

### `webdav-mcp-server` — 通用 WebDAV，最稳

| 项 | 值 |
| --- | --- |
| 包名 | `webdav-mcp-server` |
| 仓库 | `LaubPlusCo/mcp-webdav-server`（19 star） |
| 版本 | `1.0.4` |
| 发布 | 2025-03-19 |
| 运行 | `npx -y webdav-mcp-server` |
| 需要 Key | 是（WebDAV 用户名 + 应用密码） |

**适用场景**：坚果云、Nextcloud、ownCloud，以及任何兼容 WebDAV 的网盘（群晖 NAS、部分企业网盘）。

**优点**：协议层是标准的，不依赖某家网盘的私有 API，网盘改版也不会失效。文件在本机与网盘之间直传，不经过第三方服务器。

**注意**：配置时要用**应用密码**，不要用登录密码。坚果云在「账户信息 → 安全选项 → 添加应用」里生成。

---

### `sync-vault-agent` — 唯一声称全覆盖，但要谨慎

| 项 | 值 |
| --- | --- |
| 包名 | `sync-vault-agent` |
| 仓库 | `abcamus/sync-vault-agent`（0 star） |
| 版本 | `0.2.1` |
| 发布 | 2026-07-20 |
| 运行 | `npm i -g sync-vault-agent && mcp-agent init` |
| 需要 Key | 是（OAuth） |

**声称支持**：百度网盘、阿里云盘、115、夸克、OneDrive，统一管理。

**客观情况**：

- 包确实存在，2026-07 才发布，版本号还在 0.2.x；
- 仓库 **0 star**，没有社区验证；
- 走 OAuth 意味着它要拿你的网盘授权令牌。

**结论**：如果你确实要接多个国产网盘，它是目前唯一的选择，但**先隔离试跑**：

1. 用一个小号网盘账号授权，别用主账号；
2. 在独立目录里跑，观察它到底读了哪些文件；
3. 确认行为符合预期，再考虑接主账号。

**替代方案**：如果只是要「某个特定网盘 + 本地 PDF 处理」，用 `@ptbsare/netdisk-mcp-server`（夸克 + 115）比全覆盖工具更可控。

---

### `@ptbsare/netdisk-mcp-server` — 夸克 / 115 专用

| 项 | 值 |
| --- | --- |
| 包名 | `@ptbsare/netdisk-mcp-server` |
| 仓库 | `ptbsare/netdisk-mcp-server`（1 star） |
| 版本 | `1.1.1` |
| 发布 | 2026-09-11 |
| 运行 | `npx -y @ptbsare/netdisk-mcp-server` |

支持列表、查看、转存、离线下载、多平台搜索，覆盖夸克和 115。

**它填补的空白**：原始推荐里的「360 AI 云盘 MCP」和「百度网盘 MCP」，我在 npm registry 和 GitHub 上**都没找到对应的通用实现**。能找到的只有：

- `@xpert-ai/plugin-baidu-netdisk-connector`（0.2.0）——但这是 **XpertAI 平台的连接器**，不是通用 MCP server，Cursor 用不了；
- `koishi-plugin-ender-chatluna-baidu-netdisk`（1.0.0）——Koishi 聊天框架插件，同样不是 MCP。

所以「百度网盘有对应的 Agent Skill」这个说法，在 MCP 生态里目前没有可用的落地物。要用百度，只能走 `sync-vault-agent` 或自己写。

---

### `pymupdf4llm-mcp` — 本地 PDF 转 Markdown，首选

| 项 | 值 |
| --- | --- |
| 包名 | `pymupdf4llm-mcp` |
| 仓库 | `pymupdf/pymupdf4llm-mcp`（73 star，**PyMuPDF 官方**） |
| 版本 | `1.28.0` |
| 发布 | 2026-07-02 |
| 运行 | `uvx pymupdf4llm-mcp` |
| 需要 Key | 否 |

**为什么首选**：

1. **官方维护**。PyMuPDF 是这个领域的事实标准库，MCP 由同一个团队发布；
2. **纯本地**。文件不出机器，不需要 Key；
3. **输出是 Markdown**，直接喂给 LLM，不用二次清洗。

**局限**：PyMuPDF 读的是 PDF 的文字层。纯扫描件（没有文字层）需要另外的 OCR，这时候用 `mcp-pdf` 或 `pdffr-mcp`。

## 三、纠错：原始推荐里经不起验证的说法

这几条我逐个查过 registry 和仓库，结论如下。

### 1. 「pdf-mcp 有 57 种工具」— 名字撞车，功能完全不同

npm 上的 `pdf-mcp` 确实是 `0.0.3`，仓库 `alanhe421/pdf-mcp`，但它的实际描述是：

> A MCP server for **removing pages from PDFs**

也就是说，它的功能就是「删 PDF 页面」，不是 57 种工具。

**真正功能全的是 PyPI 上的 `mcp-pdf`**（`rsp2k/mcp-pdf`，2026.9.22），含文本提取、OCR、表格提取。

这两个包名极像，但完全不是同一个东西。如果你照抄了 `npx pdf-mcp`，拿到的是个删页工具。

### 2. 「nutstore-mcp 用 uvx 运行」— 这条是对的，但它在 PyPI 不在 npm

`nutstore-mcp@1.1.0` 存在于 **PyPI**，仓库 `silverze/nutstore-mcp`（1 star）。`uvx nutstore-mcp` 可以直接跑。

它走 WebDAV 协议，所以虽然名义上"专为坚果云设计"，实际上能连任何兼容 WebDAV 的网盘。既然这样，直接用更通用的 `webdav-mcp-server` 也差不多，区别在于 `nutstore-mcp` 做了坚果云的默认配置。

### 3. 「360 AI 云盘 MCP 支持 Stdio、HTTP、SSE 三种传输」— 找不到

我在 npm 搜索 `mcp baidu netdisk`、`mcp quark pan`、`mcp aliyundrive`，以及 GitHub 搜索，都没有找到通用的 360 云盘 MCP 实现。唯一沾边的是 `@xpert-ai/plugin-baidu-netdisk-connector`，但它是 XpertAI 专属。

**结论：这条未能核实，本仓库不收录。** 如果你的信息源有具体仓库地址，欢迎提 issue 补充。

### 4. 「pdffr-mcp 用 npx 装」— 这条是对的

`pdffr-mcp@0.1.1` 在 npm，`npx -y pdffr-mcp` 正确。但要记住：**PyPI 上没有这个包**。

### 5. 「fastocr-mcp 依赖 FastOCR API」— 这条是对的，但注册表说错了

它在 **PyPI**（`0.3.0`），不是 npm。`uvx fastocr-mcp` 才对。

### 6. 「sync-vault-agent 零配置开箱即用」— 乐观了

包存在，`npm i -g` 能装。但「零配置」这个说法忽略了两个事实：

- 它要走 OAuth，你得为每个网盘授权一次；
- 它 2026-07 才发布，仓库 0 star，没有第三方验证过稳定性。

「零配置」在宣传语境里指的是「不用手写配置文件」，不是「不用管授权和风险」。

## 四、Dify 侧：逐个核实

Dify 的官方插件仓库是 `langgenius/dify-official-plugins`，分 `datasources`、`tools`、`models`、`agent-strategies` 等目录。我直接读了目录列表。

### 官方数据源（已确认存在）

```
datasources/
├── aws_s3_storage
├── azure_blob
├── box_datasource
├── brightdata_datasource
├── confluence_datasource
├── dropbox_datasource
├── firecrawl_datasource
├── github
├── gitlab_datasource
├── google_cloud_storage
├── google_drive
├── jina_datasource
├── notion_datasource
├── onedrive
├── sharepoint_datasource
├── tavily_datasource
└── tencent_cos_storage
```

原始推荐说的「OneDrive、Google Drive、Box、AWS S3、腾讯 COS」**全部确认存在**。这条是对的。

### 「WebDAV Datasource 是事实标准」— 不成立

**官方 datasources 目录里没有任何 webdav 条目。** 唯一能找到的是社区插件 `shaba/dify-datasource-webdav`，**1 star**。

要区分另一种情况：官方 `tools` 目录里有个 `nextcloud` 插件（作者 `langgenius`，v0.1.7），描述写明走 WebDAV，可列出/下载/上传/搜索文件。但它是 **tool 插件**，只能在工作流的 Agent 节点里调用，**不会出现在「知识库 → 数据源」的摄取列表里**，因此解决不了「网盘文件直接灌进知识库」。

它能用，但：

- 单星、单人维护，随时可能停更；
- 没有官方背书，Dify 升级后需要自行跟进兼容性。

所以准确的说法是「WebDAV 是社区方案里唯一的选择」，不是「事实标准」。

如果坚果云是你的主要网盘，另一个思路：**坚果云支持 WebDAV，而 Dify 的流程可以是「先用本地脚本把文件同步到本地，再上传到 Dify 知识库」**，绕开插件。

### `MinerU` — 确认是官方插件

```
tools/
├── mineru          ✅
├── paddleocr       ✅
├── nextcloud       ✅（WebDAV 协议，但只能在工作流里调用）
├── feishu_document
└── lark_document
```

MinerU 在官方 tools 目录里，确认存在。它能自动检测扫描版 PDF 并启用 OCR，把复杂 PDF（公式、表格、多栏）还原为结构化 Markdown/JSON。

同目录下还有 **PaddleOCR 官方插件**，中文识别有优势，且可自托管。

### `Upstage Document Parse` — 官方目录里没有

在 `tools` 和 `datasources` 两个目录里都没找到。标注为「第三方/未核实」。

如果你的信息源有 Dify 插件市场的具体链接，欢迎补充。

## 五、Windows 环境实操注意

当前机器：Windows 10.0.19045，Node 22.22.3，npm 11.14.1，Python 3.10.16，uv 0.9.2。

### `npx` 类工具

```bash
npx -y webdav-mcp-server
```

Windows 下 `npx` 首次运行会下载包，体积较大时需要几十秒。如果卡住，检查 npm 源。

### `uvx` 类工具

```bash
uvx pymupdf4llm-mcp
```

`uv` 已装（0.9.2）。`uvx` 会在独立环境里跑，不污染全局 Python。

### 一个坑：npm 报错 `config prefix cannot be changed from project config`

```
npm error config prefix cannot be changed from project config: C:\Users\Administrator\.npmrc
```

这是 `~/.npmrc` 和项目级 npm 配置冲突导致的。**不影响 `npm view` 这类查询命令**，但会影响 `npm i -g`。

如果需要全局安装，先检查：

```bash
npm config get prefix
```

确保 `~/.npmrc` 里的 `prefix` 是绝对路径，且没有在项目目录下的 `.npmrc` 里重复定义。

## 六、隐私分级

选工具时按这个顺序判断：

| 级别 | 特征 | 代表工具 | 适合什么数据 |
| --- | --- | --- | --- |
| A. 完全本地 | 文件不出机器，无网络请求 | `pymupdf4llm-mcp`、`pdffr-mcp`、`mcp-pdf`、`macos-vision-mcp` | 教材、试卷、含个人信息的文档 |
| B. 本地直传网盘 | 文件在你和网盘之间，不经第三方 | `webdav-mcp-server`、`nutstore-mcp` | 自己的资料 |
| C. OAuth 授权第三方 | 第三方服务持有你的令牌 | `sync-vault-agent` | 非敏感资料，小号试跑 |
| D. 云端 API | 文件上传到服务商 | `fastocr-mcp`、MinerU 云端版 | 公开资料 |

给孩子处理的教材和试卷，**优先 A 或 B**。A 类工具已经够用，没必要为了「功能全」把资料传到别人的服务器上。
